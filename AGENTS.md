# Правила работы с timetable-service

## Источники требований

- Перед изменением читать относящиеся к задаче разделы [TASK.md](TASK.md),
  [CONTRIBUTING.md](CONTRIBUTING.md), актуальные OpenSpec proposal, specs, design и tasks
  в `openspec/`, затем соответствующий код и тесты. Сведения о каркасе — в [SCAFFOLD.md](SCAFFOLD.md).
- HTTP-контракт определяется `openapi.yaml`, события — `asyncapi.yaml`, интеграция
  с people-stub — `stubs/people-stub/stub-openapi.yaml`.
- При противоречии документов и кода явно сообщать о нём. Изменение архитектурного решения
  согласовывать и отражать в design; контракт не подгонять под реализацию.
- Процесс веток, коммитов и слияния — по `CONTRIBUTING.md`.

## Ответственность кода

- `app/api/` — HTTP-маршруты и получение зависимостей.
- `app/schemas/` — Pydantic-схемы запросов и ответов.
- `app/services/` — предметные сценарии, общие бизнес-проверки и границы транзакций.
- `app/db/repositories/` — операции хранения; `app/db/models/` — SQLAlchemy-модели.
- `app/maintenance/` — seed/reset напрямую через БД, без people-stub и предметной валидации.
- Предметные маршруты вызывают сервисы; SQL-запросы размещаются в репозиториях.
  Служебные маршруты не требуют дополнительных слоёв ради единообразия.
- Схемы проверяют структуру и значения входных данных; проверки с обращением к БД,
  Clock или people-stub выполняются в предметном сценарии.
- FastAPI `Request`, `Depends` и весь `AppContext` не передавать в предметные сервисы
  и репозитории. Передавать необходимые зависимости явно.

## Сессии и транзакции

- Сервис получает фабрику сессий и открывает существующий `session_scope` вокруг целой
  атомарной операции. Не объединять сценарий вызовами методов с независимыми транзакциями.
- Репозитории получают одну сессию этой операции; не вызывают commit/rollback.
  Функции seed/reset также не завершают транзакцию самостоятельно.
- Исключения, требующие отката, должны выйти из `session_scope`; не подавлять их
  с возвратом успешного результата. Учитывать ошибки как при запросах, так и при commit.
- События публиковать после успешного commit согласно заданию.
- Атомарность транзакции не заменяет ограничения БД и защиту от конкурентных нарушений.

## Типы, схемы и ошибки

- Сохранять mypy strict и настройки ruff в `pyproject.toml`. Не ослаблять проверки;
  подавления типов — только с кодом ошибки и объяснением причины.
- Использовать UUID, типизированные ORM-поля и существующие `LessonStatus`/`LessonFormat`.
- Различать nullable-поле и необязательное присутствие поля. Обязательные поля ответа
  сохранять, включая значения `null`.
- API преобразует загруженные ORM-данные в Pydantic-схемы. Не рассчитывать на загрузку
  дополнительных данных после закрытия сессии.
- Ожидаемые ошибки сценариев наследовать от `ServiceError`; конкретные ошибки преобразовывать
  в контрактные HTTP-ответы централизованно в `errors.py`.
- Сохранять `ApiError` и формат `{"error": {"code", "message", "details"}}`.
- Отсутствие строки репозиторий возвращает как `None`; сервис определяет ошибку сценария.
- Использовать исключения SQLAlchemy для технических ошибок БД. Преобразовывать только
  распознанные нарушения ограничений; неизвестные ошибки не выдавать за ожидаемые 404/409.

## Асинхронность и время

- Не выполнять блокирующие операции в event loop. Независимые вызовы people-stub выполнять
  параллельно согласно заданию; одну `AsyncSession` не использовать одновременно в нескольких задачах.
- Ресурсы закрывать через контекстные менеджеры или `finally`;
  фоновые задачи завершать при остановке приложения.
- Текущее предметное время получать через `Clock`. Системное время допустимо только
  внутри реализации часов; не использовать серверный NOW вместо Clock.
- Время ответов и событий сериализовать через `to_iso_z`;
  временные значения seed сохранять из файлов.

## Имена и пояснения

- Модули и функции называть в `snake_case`, классы — в `PascalCase`;
  имена должны обозначать предметную сущность или действие.
- Комментарии и docstring добавлять для неочевидных причин, ограничений, побочных эффектов
  и контрактов. Не пересказывать код и не требовать docstring для каждой функции.

## Логирование

- Использовать стандартный `logging` и логгер модуля `logging.getLogger(__name__)`;
  уровень задаётся через `LOG_LEVEL`.
- Настраивать логирование в точках входа, не в сервисах и репозиториях.
- Неожиданные ошибки записывать с traceback на границе обработки: HTTP-обработчик,
  фоновая задача или команда. Одну ошибку не логировать повторно в каждом слое.
- Ожидаемые ошибки клиента и предметные отказы не записывать как внутренние ошибки с traceback.
- Сообщение должно объяснять операцию и содержать полезные идентификаторы.
  Не записывать пароли, строки подключения с учётными данными и полные тела запросов.
- Сообщения об успешной записи данных создавать после commit.

## Проверки и объём изменений

- Выбирать проверки по изменённому поведению: unit для логики, PostgreSQL для ограничений
  и транзакций, HTTP/контрактные проверки для API.
- Использовать существующие фикстуры. Обычные интеграционные тесты изолировать внешним rollback;
  конкурентные тесты с настоящим commit должны очищать собственные данные в `finally`.
- Проверять границы, ошибки и откат, а не только успешный сценарий.
  Зелёные тесты каркаса не доказывают реализацию новых требований.
- Сохранять текущие фреймворк и зависимости. Новые абстракции и рефакторинг предлагать
  только для конкретной потребности; не вводить универсальные базовые репозитории
  и новый менеджер транзакций.

## Команды

Актуальные рецепты — в [justfile](justfile); обычные проверки могут создавать локальные кэши.

| Команда | Назначение и изменения |
| --- | --- |
| `just lint`, `just typecheck`, `just test` | Ruff, mypy, unit-тесты; без рабочей БД |
| `just check` | Эти три проверки; PostgreSQL и e2e не включает |
| `just lint-commits` | Проверка истории без изменения Git |
| `just test-db-test` | Изменяет тестовую БД; отдельные тесты выполняют настоящий commit |
| `just e2e-public` | Меняет данные приложения, часы, заглушку и брокер; создаёт отчёт |
| `just fmt` | Изменяет файлы |
| `just test-db-init` | Создаёт локальный `.env.test` |
| `just test-db-up`, `just test-db-down` | Меняют окружение; остановка уничтожает данные тестовой БД |
| `just test-app` | Запускает приложение с тестовой БД; запросы могут менять её данные |
| `just test-container-build` | Собирает тестовый образ |
| `just test-container-start 0` / `1` | Миграции тестовой БД; при `1` также seed |
| `just migrate`, `just test-db-migrate` | Меняют схему выбранной БД |
| `just seed`, `just test-db-seed` | Меняют данные выбранной БД |
| `just migration "..."`, `just test-db-migration "..."` | Создают и форматируют файлы миграций |
| `just up` | Меняет окружение; может применить миграции и seed |
| `just down` | Удаляет контейнеры и тома основного стека, включая данные |
| `just setup`, `just merge-change <id>` | Меняют настройки Git или ветки и историю; процесс — в CONTRIBUTING.md |

Перед проверкой с изменением данных определить целевое окружение;
для интеграционных проверок использовать отдельную тестовую PostgreSQL.

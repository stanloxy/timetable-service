# Design

## Граница транзакции и события

HTTP-маршруты передают издателя в сценарии confirm, cancel и reschedule как явную зависимость. Сервис занятий выбирает событие по успешному переходу и собирает снимок полей внутри существующего `session_scope`. Предыдущий статус для отмены читается под блокировкой до записи `CANCELLED`. Для переноса снимки исходного занятия и преемника берутся из той же транзакции. У преемника уже есть UUID, созданный сервисом. Границы транзакций, порядок блокировок ресурсов и ограничения PostgreSQL из WP-05 сохраняются.

Схемы событий описывают конверт и payload по `asyncapi.yaml`, преобразуют UUID и UTC-метки для JSON. В `occurred_at` используется тот же снимок `Clock`, что и для `updated_at` перехода. `to_iso_z` даёт суффикс `Z`. Для дат занятия сохраняются дробные секунды при их наличии. Сервис вызывает издателя после выхода из `session_scope`, когда commit завершён. Исключение внутри транзакции или при commit прерывает этот путь. Репозитории отвечают за операции хранения. HTTP-слой передаёт зависимости и формирует ответ.

## RabbitMQ и результат публикации

При `BROKER=rabbitmq` инфраструктурный адаптер использует `BROKER_URL`. `aio-pika` устанавливается как зависимость приложения, чтобы Docker включил её при сборке без групп разработки и E2E. Compose ждёт запуска контейнера RabbitMQ. Доступность AMQP отражает readiness приложения.

Издатель объявляет долговечный topic exchange `wa.events`, отправляет JSON с routing key `timetable.<EventType>`, постоянным режимом доставки, `content_type=application/json` и `message_id=event_id`. Для отправки используются publisher confirms и обязательная маршрутизация. Возврат сообщения означает, что подходящей очереди нет. Подтверждение RabbitMQ относится к приёму брокером. Подписчики обрабатывают сообщения из своих очередей независимо.

На подготовку соединения, канала и exchange и ожидание подтверждения отводится один общий бюджет в две секунды. Временный сбой подготовки допускает до трёх попыток в этом бюджете. После вызова `publish` повторная отправка этого события не выполняется. Обрыв или таймаут в этой фазе может означать как потерю события, так и приём сообщения с потерянным подтверждением. Это ограничивает отправку одним вызовом `publish` на переход. RabbitMQ может повторно доставлять сообщения подписчику, который обрабатывает их с учётом `idempotency_key`.

При итоговом сбое адаптер пишет одну запись уровня `ERROR` с причиной, типом события, `event_id` и ID исходного занятия. Журнал исключает credentials и payload. HTTP возвращает сохранённый результат согласно контракту. При сбое возможна потеря события, в том числе при остановке процесса между commit и отправкой. Transactional outbox дал бы возможность восстановить отправку после сбоя и потребовал бы отдельного хранения и процесса доставки.

## Readiness и жизненный цикл

Lifespan создаёт адаптер без ожидания RabbitMQ и закрывает AMQP-ресурсы при остановке. Проверка readiness и публикация открывают соединение по требованию. После отказа следующий вызов может подключиться заново без перезапуска процесса. Readiness выполняет AMQP-запрос к брокеру, поэтому открытый локальный объект соединения сам по себе не означает `broker: ok`. Проверка идёт параллельно с `SELECT 1`. Каждая зависимость имеет собственный лимит в две секунды. `/health/live` отвечает по живости процесса.

## Проверка порядка

Очередь E2E создаётся и привязывается до HTTP-запроса. Интеграционный тест проверяет видимость зафиксированного перехода из отдельного соединения PostgreSQL прямо в момент вызова издателя. Тест ошибки commit проверяет откат и отсутствие вызова. Так проверяются и фактический порядок, и отказ до границы публикации.

# Design

## Context

WP-02 добавляет получение справочных данных для проверки занятия (FR-12) и воспроизводимую проверку параллелизма (NFR-07). Сборка возвращает профиль преподавателя, его недельную доступность и, для очного занятия, аудиторию. Проверки вместимости, нагрузки и доступности по времени относятся к WP-03.

## Decisions

### HTTP-клиент и типы

Используем `httpx.AsyncClient`. `httpx` уже используется в тестах. Объявляем его в runtime-зависимостях, поскольку образ приложения собирается без групп `dev` и `e2e`. `MockTransport` позволяет проверять запросы и ответы без сети.

Клиент размещаем в `app/clients/people.py`, модели ответов заглушки — в `app/clients/people_models.py`. У каждого из трёх эндпоинтов свой метод и своя Pydantic-модель ответа по контракту заглушки. Идентификаторы представлены как `UUID`, дневной лимит допускает дробное значение, вместимость представлена целым числом. Окна доступности описаны отдельной моделью с днём недели и локальными границами `from` и `to`. Часовой пояс передаётся именем IANA.

### Настройки и жизненный цикл

Один `AsyncClient` создаётся на время `lifespan` приложения с адресом из `STUB_BASE_URL`. `lifespan` закрывает клиент через асинхронный контекстный менеджер. При старте клиент создаётся без обращения к заглушке. В тестах, которые собирают контекст напрямую, зависимость передаётся явно.

Каждый HTTP-вызов обёрнут в свой `asyncio.timeout()` со значением `STUB_TIMEOUT_MS`, переведённым в секунды. Этот лимит охватывает получение ответа целиком. `STUB_TIMEOUT_MS` остаётся единственным источником лимита. Лимиты `httpx` по этапам запроса сами по себе не ограничивают суммарную длительность вызова.

### Параллельная сборка

Сборка размещается в `app/services/` и получает клиент как явную зависимость. Она запускает профиль и доступность одновременно. Для `IN_PERSON` одновременно запускается и запрос аудитории. При успехе сборка возвращает один типизированный результат. Операция работает без сессии БД.

При обычном отказе сборка дожидается всех уже запущенных вызовов. Каждый из них ограничен собственным таймаутом. Если отменяется сама операция сборки, незавершённые вызовы отменяются, а сборка дожидается их завершения. Завершение при первом отказе сократило бы ожидание при раннем сбое, но итоговый код зависел бы от порядка ответов.

### Ошибки

Клиент возвращает `None` для `404` и сообщает о техническом отказе или таймауте через исключения клиентского слоя. Сервис преобразует эти исходы в ожидаемые ошибки из `app/services/exceptions.py`, наследуемые от `ServiceError`. Преобразование в контрактный HTTP-ответ выполняется в `app/errors.py`.

Когда получено несколько ожидаемых отказов, сервис выбирает один по фиксированному приоритету:

1. Таймаут вызова — `504 UPSTREAM_TIMEOUT`.
2. `5xx`, сетевой сбой, некорректное тело ответа `200` или неожиданный HTTP-статус — `502 UPSTREAM_UNAVAILABLE`.
3. `404` профиля или доступности — `422 INSTRUCTOR_NOT_FOUND`.
4. `404` аудитории — `422 CLASSROOM_NOT_FOUND`.

Приоритет при нескольких отказах и трактовка непригодного ответа являются решениями WP-02. Неожиданные ошибки приложения продолжают обрабатываться штатным обработчиком.

### Проверки

Запросы, разбор ответов и преобразование ошибок проверяем без сети. Отдельно проверяем закрытие клиента, выбор одной и той же ошибки при разном порядке отказов и отмену незавершённых вызовов при отмене сборки.

В async-тесте запускаем одни и те же вызовы фейкового клиента последовательно и через сервис сборки. Счётчик активных вызовов проверяет фактическое перекрытие, а `time.perf_counter()` измеряет длительность. Проверку времени строим на сравнении двух запусков с запасом на планирование задач. В README записываем команду и реальные замеры.

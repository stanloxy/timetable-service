# Design

## Context

WP-04 реализует FR-03 и FR-05 по `openapi.yaml` и TASK.md. WP-01 даёт чтение и модели, WP-03 даёт общую проверку BR-01…BR-07 и порядок блокировок PostgreSQL.

## Decisions

### Список занятий

HTTP-слой проверяет UUID v4, статус, даты ISO 8601 со смещением и пагинацию. Все ошибки известных query-параметров возвращают `422 VALIDATION_ERROR` с публичным именем в `details.fields`, включая `from`, `to` и ошибку разбора целого числа. Эта трактовка ограничена маршрутом списка, у которого контракт предусматривает `422`. Неизвестные параметры игнорируются. При повторе известного скалярного параметра используется последнее значение.

Сервис открывает сессию для чтения. Репозиторий строит один отфильтрованный набор по заданным условиям, вычисляет `COUNT(*)` до пагинации и формирует страницу по `starts_at ASC, id ASC`. Результат подсчёта сохраняется при пустой странице, например через `LEFT JOIN` страницы к результату подсчёта. Один SQL-запрос даёт согласованные `items` и `total` при одновременной записи. Простой оконный подсчёт по строкам страницы терял бы `total` при смещении за конец выборки. HTTP-слой сериализует занятия через существующий `LessonResponse`.

Условия периода применяются независимо к началу занятия. Равные и обратные границы дают пустой набор по определению фильтра. Корректный UUID без совпадений также даёт пустой набор. Сервис использует сохранённые данные и обходится без people-stub.

### Частичное редактирование

На HTTP-границе принимаются только поля `LessonPatch`. Пустой объект даёт `422 VALIDATION_ERROR` с `details.fields.body`, лишние поля — `422 VALIDATION_ERROR` с их именами. Невалидный JSON и неверные JSON-типы, включая `null` у полей кроме `classroom_id`, дают `400 BAD_REQUEST`. Контрактные типы и форматы проверяются до вызова сервиса.

Сервис начинает `session_scope` и через репозиторий читает строку занятия с `SELECT ... FOR UPDATE`. Отсутствующая строка даёт `404 NOT_FOUND`. Любой статус кроме `PLANNED` даёт `409 LESSON_NOT_EDITABLE` с `details.current_status` до BR-01…BR-07. Сервис строит кандидата из актуальной записи и переданных значений. Пропущенная аудитория сохраняется, явно переданный `null` очищает её. Для перехода с `IN_PERSON` на `ONLINE` клиент передаёт новый формат и `classroom_id: null`.

Общая проверка выполняется в порядке WP-03. Для BR-05 и BR-06 исключается `exclude_lesson_id`, равный ID редактируемой строки. Сервис присваивает значения только после успешной проверки, получает `updated_at` из `Clock` и сохраняет `id`, `group_id`, `status`, `created_at`, `rescheduled_from_id` и `cancel_reason`. Действующие ограничения БД продолжают проверять длительность, соответствие формата и аудитории и внешние ключи. За отсутствие пересечений при записи через API отвечает общий протокол блокировок. Успех возвращается после commit, исключения приводят к rollback. PATCH выполняется без событий.

### Конкуренция

PATCH блокирует одну редактируемую строку до чтения значений для слияния. После BR-04 и перед запросами BR-05 и BR-06 общая проверка берёт транзакционные advisory locks по объединению прежних и новых ресурсов. POST берёт тот же тип блокировок для ресурсов кандидата. Репозиторий преобразует пары «тип ресурса и UUID» в ключи, удаляет дубли и сортирует весь набор численно перед захватом. Оба сценария читают другие занятия обычным `SELECT` и удерживают блокировки до конца транзакции.

- При конкуренции за целевой ресурс отдельный запрос BR-05 после ожидания при `READ COMMITTED` видит зафиксированный результат предыдущего запроса. При пересечении ожидающий запрос возвращает `409 SCHEDULE_CONFLICT`.
- Если POST ждёт прежний ресурс, который PATCH освобождает, после commit он увидит освободившийся интервал. После rollback он увидит прежнее занятие. Блокировки только новых ресурсов позволили бы POST отклониться по прежней записи в середине переноса, который затем успешно завершился бы.
- Два PATCH одной строки сериализуются по блокировке строки. Второй сливает свои поля с версией, доступной после завершения первого. Правки разных полей сохраняются вместе. При разных значениях одного поля остаётся значение последнего успешно зафиксированного PATCH. Если его кандидат нарушает правила, сохраняется результат предыдущей успешной правки.
- Два PATCH разных строк при смене ресурсов берут ключи в едином порядке. Каждый запрос держит только свою строку и не запрашивает блокировку строки конкурента в проверке пересечений.

# Proposal

## Why

Сервис уже читает расписание и получает справочные данные из people-stub. Чтобы создать занятие, нужно проверить занятость преподавателя, группы и аудитории, в том числе при одновременных запросах. Клиенту также нужна возможность выполнить ту же проверку до записи (FR-01, FR-02).

## What Changes

- Добавить `POST /lessons`. При успешной проверке BR-01…BR-07 маршрут сохраняет занятие в `PLANNED` и возвращает `201 {lesson, warnings}`.
- Добавить `POST /lessons/validate`. Прикладные отказы, соответствующие `409` при создании, возвращаются в `violations` при `200`. Проверка выполняется без записи и событий.
- Применять hard-правила в порядке задания. При конфликте возвращать каждое совпадение занятия и ресурса с точными границами пересечения. При успешной проверке выдавать предупреждения о превышении дневной нагрузки и выходе за окно доступности.
- Защитить поиск и вставку транзакционными блокировками по ресурсам. Это позволяет вернуть полный список пересечений после ожидания конкурирующей записи и обойтись без миграции. Операции записи через API должны соблюдать общий протокол. PostgreSQL exclusion constraints защищали бы также прямые записи, но потребовали бы миграции и отдельного чтения для восстановления полного ответа после конкурентного отказа.

## Capabilities

### New Capabilities

- `lesson-scheduling` — создание и проверка занятия по BR-01…BR-07.

### Modified Capabilities

Нет.

## Impact

Изменения затронут маршруты и схемы занятий, сервис и репозиторий, обработку предметных ошибок, сериализацию времени занятий и тесты. Для справочных данных используется существующая сборка WP-02. Список и редактирование занятий, операции жизненного цикла, брокер, readiness и кэш находятся за пределами пакета. HTTP-контракт задан в `openapi.yaml`.

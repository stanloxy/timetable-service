# Design

## Сценарии HTTP

Маршруты принимают тела по `openapi.yaml`, передают сервису явные зависимости и формируют ответ из результата сохранения. Схемы различают отсутствующие поля и явный `null`. Для `cancel` отсутствие тела допустимо, а JSON `null` в качестве тела классифицируется как неверный тип. `reason` сохраняется без преобразования. Ошибки структуры обрабатываются в HTTP-слое, ошибки предметных переходов преобразуются централизованно в контрактный ответ.

Для PATCH и переноса сервис использует типы уже провалидированных словарей `LessonPatch` и `LessonReschedule` из `app/schemas/lessons.py`. Эти импорты нужны только для статической проверки типов. Репозиторий списка получает `LessonFilters` из `app/db/lesson_filters.py`. HTTP-параметры и ограничения пагинации обрабатываются в схеме запроса.

Каждый HTTP-переход открывает `session_scope` и читает занятие репозиторием через `SELECT … FOR UPDATE`. Если строки нет, сервис возвращает предметную ошибку для `404 NOT_FOUND`. Проверка текущего статуса выполняется под блокировкой и предшествует BR-01…BR-07 для переноса и BR-08 для завершения. `complete` читает `Clock.now()` после проверки статуса и использует тот же момент для сравнения с `ends_at` и для записи `updated_at` либо для деталей отказа. Все HTTP-ответы об успешной записи формируются после commit.

## Перенос и общий протокол записи

Сервис строит кандидата из обязательных новых дат и полей актуальной исходной строки. Пропущенные `instructor_id`, `classroom_id` и `format` наследуются. Явный `classroom_id: null` очищает аудиторию. Группа всегда берётся из исходной строки. Сервис передаёт кандидата в `check_lesson` с `exclude_lesson_id` исходного занятия для BR-05 и BR-06 и с прежними ресурсами для блокировок.

После BR-04 и до запросов BR-05 и BR-06 репозиторий захватывает `pg_advisory_xact_lock` по объединению прежних и новых ключей группы, преподавателя и аудитории. POST, PATCH и перенос используют одинаковое вычисление ключей, удаление дублей и сортировку всего набора. При `READ COMMITTED` отдельный запрос после ожидания блокировок читает результат зафиксированной конкурентной записи. Запросы пересечений читают другие занятия без блокировки их строк. POST берёт только ключи ресурсов. PATCH и перенос блокируют каждый свою исходную строку перед ключами.

После успешной проверки сервис устанавливает исходному занятию `RESCHEDULED` и добавляет преемника в `PLANNED`. Оба изменения используют одну сессию и одну транзакцию. Часы сервиса дают общий момент для `updated_at` исходного и `created_at` и `updated_at` нового занятия. При ошибке SQL или отказе до завершения commit транзакция откатывает оба изменения. Повторный перенос после успешной записи видит `RESCHEDULED` и отклоняется до предметных проверок. Ограничение `uq_lessons_rescheduled_from_id` независимо защищает единственность преемника, а внешний ключ защищает ссылку на исходное занятие.

При переносе и PATCH одной строки ожидающий запрос работает с версией после commit конкурента. При разных строках общий порядок ключей защищает от взаимного ожидания по ресурсам. Создание или правка, ожидающие ключ прежнего ресурса, увидят освобождённый интервал после успешного переноса либо исходное занятие после отката. `cancel` освобождает интервал сменой статуса под блокировкой строки. `confirm`, `complete` и sweeper оставляют занятие в наборе активных статусов для проверки расписания.

## Sweeper

`build_context` регистрирует `lesson-status-sweeper` с фабрикой сессий и общим `Clock`. Один запуск берёт один снимок времени. Репозиторий в одном SQL-выражении выбирает и блокирует подходящие строки в порядке `id`, обновляет их статус и `updated_at` и использует `RETURNING` для подсчёта обновлений. Предикат — `status = CONFIRMED AND starts_at <= now`. Задача возвращает подсчёт после успешного выхода из `session_scope`.

В PostgreSQL при `READ COMMITTED` ожидающее блокировки чтение перепроверяет предикат на актуальной версии строки. После commit отмены или переноса строка выпадает из выборки. Если sweeper зафиксировался первым, HTTP-сценарий видит `IN_PROGRESS` и отклоняет отмену или перенос. Одинаковый порядок захвата строк при параллельных запусках и предикат по статусу обеспечивают однократный подсчёт перехода. Ручной маршрут и периодический цикл вызывают одну зарегистрированную задачу. Режим и интервал определяются существующим lifespan и настройками.

## Подключение событий в WP-06

Точка вызова издателя — после успешного выхода из `session_scope`. В WP-06 нужные для событий значения следует собрать внутри транзакции из версии, на которой выполнен переход. `LessonConfirmed` использует сохранённые поля занятия. `LessonCancelled` дополнительно требует предыдущий статус и `reason`, включая `null`. Для `LessonRescheduled` требуются ID исходного занятия и преемника, общая группа, исходный преподаватель и оба интервала с преподавателем и аудиторией каждого. `occurred_at` берётся из `Clock` в момент операции. Ключ идемпотентности строится по ID исходного занятия. Для RabbitMQ контракт задаёт topic exchange `wa.events` и routing key `timetable.<EventType>`. Транспорт, формирование событий и readiness с брокером входят в WP-06.

## Проверки

Тесты HTTP используют существующие фикстуры с внешним rollback и управляемыми часами. Конкурентные тесты используют отдельную PostgreSQL, отдельные соединения, фактическое ожидание блокировки и очистку своих данных. Проверка периодического режима использует существующий цикл с управляемым завершением. Регрессия E2E-01 и E2E-02 запускается на обновлённом стеке. Полный E2E-17 требует издателя из WP-06.

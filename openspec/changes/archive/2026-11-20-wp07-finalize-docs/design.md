# WP-07. Документация и приёмочная проверка

## Источники для README

За основу берём шесть заголовков из Приложения A TASK.md. Запуск проверяем по Compose, entrypoint, justfile и тестовым фикстурам. Решения и ограничения описываем по коду, контрактам и завершённым OpenSpec changes. Так сохраняется связь между описанием и поведением, которое можно воспроизвести.

RabbitMQ используется как выбранный брокер. Сервис вызывает издателя после коммита PostgreSQL. Издатель ожидает подтверждение брокера в пределах общего таймаута и повторяет только подготовку до вызова `publish` при временных отказах. При ошибке отправки изменение в PostgreSQL остаётся зафиксированным, а журнал содержит исход публикации. Потеря подтверждения оставляет исход неопределённым. Гарантия восстановления потерянного события потребовала бы отдельного механизма доставки.

AI notes опираются на уже зафиксированные примеры и подтверждённые действия автора в WP-07. Оценка автора до старта — 0,5 ч. Фактическое время берём от автора и округляем по CONTRIBUTING.md.

## Приёмка

Проверку привязываем к SHA. Для Compose нужен чистый клон, отдельное имя проекта, новый том и свободные порты. Верхняя граница в пять минут считается от запуска `docker compose up --build` до HTTP 200 от `/health/ready` с обоими статусами `ok`. Первое применение миграций видно в логах entrypoint. Команда `just test-db-migrate` дополнительно проверяет миграции на пустой отдельной PostgreSQL.

Публичные E2E запускаем на том же изолированном стеке. Фикстуры меняют данные, часы, состояние заглушки и очередь брокера. Интеграционные тесты используют отдельную PostgreSQL. Замер async-кейса использует фейковый клиент с заданной задержкой. Сохраняем исходные результаты WP-06 и отдельно записываем результаты проверяемого коммита.

В GitHub Actions сверяем `check` и `lint-commits` по SHA. Результаты сборки образа, статического анализа и модульных тестов в CI дополняют локальные проверки readiness, миграций и E2E.

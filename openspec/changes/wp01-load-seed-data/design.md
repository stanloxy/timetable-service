# Design

## Context

Мотивация и границы пакета описаны в proposal.md, проверяемое поведение — в specs/. Каркас уже предоставляет async-сессии SQLAlchemy и `session_scope` в `src/app/db.py`.

## Goals / Non-Goals

Цель — использовать существующий каркас, единые границы транзакций и проверяемые ограничения PostgreSQL. Предметные проверки создания и переноса, вызовы people-stub, брокер и readiness с брокером остаются следующим пакетам. Нативные PostgreSQL enum и новый менеджер транзакций не требуются.

## Decisions

### Границы транзакций

Используем существующий `session_scope` через `async with` вокруг целой операции. Он создаёт и закрывает сессию, выполняет commit при успехе и rollback при исключении. Репозитории и загрузчик seed получают сессию извне и не выполняют commit или rollback самостоятельно. Очистка и загрузка seed при reset используют одну сессию и одну транзакцию: ошибка восстановления откатывает также очистку.

Альтернативы: отдельный менеджер транзакций дублирует готовый механизм; commit внутри репозиториев или загрузчика разделил бы атомарный reset на независимые операции. Обе альтернативы отвергнуты.

### Обычный seed и reset

Обычная загрузка добавляет отсутствующие записи, не меняя существующие seed-записи и дополнительные данные. Reset очищает предметные данные и восстанавливает исходные значения из файлов в одной транзакции, не обращаясь к часам. Ограничения БД продолжают действовать; предметная валидация и people-stub не вызываются.

Альтернативы: перезапись seed-записей при обычном запуске могла бы затирать изменения; загрузка через API создала бы зависимость от следующих пакетов и внешнего сервиса; загрузка миграцией смешала бы изменение схемы с повторяемой операцией наполнения. Эти варианты отвергнуты.

### Защита ссылок и истории

Целостность локальных ссылок защищается FK, не более одного преемника — уникальностью ненулевого `rescheduled_from_id`, запрет самоссылки — CHECK. Удаление используемой группы или исходного занятия запрещается FK без каскадного удаления. Эти ограничения действуют также при прямой загрузке данных. Транзакция защищает атомарность reset; проверки переходов статусов и предметные операции переноса относятся к следующим пакетам.

Альтернативы: одних проверок приложения недостаточно для прямых записей и конкурентного создания преемников; каскадное удаление могло бы уничтожить связанные занятия и историю. Эти варианты отвергнуты.

### Структура и чтение

Модели размещаются в `src/app/models/`, репозитории — в `src/app/repositories/`, сервисы — в `src/app/services/`, HTTP-маршруты и схемы — в `src/app/api/`. Сохраняем существующий пакет `app`. Репозиторий получает запись по UUID через переданную сессию, сервис обрабатывает отсутствие ресурса, API сериализует типизированный ответ. Для ошибок используется существующий механизм платформы. Ответы не оборачиваются в `lesson` или `group`.

Альтернатива — вызов репозитория прямо из маршрута — проще для двух GET, но выбран сервисный слой для отделения сценариев от HTTP и последующего расширения. Дополнительные универсальные базовые репозитории не нужны.

### Типы и ограничения

Идентификаторы хранятся как UUID, строки — text, численность — integer, временные поля — timestamptz. Статус и формат хранятся строками с именованными CHECK, а не отдельными PostgreSQL enum: изменение списка значений и откат миграции проще. Допустимые значения соответствуют контракту.

NOT NULL, PK, FK, UNIQUE и CHECK реализуют правила из specs/timetable-data/spec.md. CHECK длительности от 30 минут до 8 часов также исключает нулевой и отрицательный интервал; отдельное дублирующее ограничение не требуется. CHECK формата согласует наличие аудитории с форматом. FK имеют поведение NO ACTION без каскада. Идентификаторы преподавателей и аудиторий не имеют локальных FK.

Временные поля seed берутся из файлов; вывод использует `to_iso_z`. Новые временные значения в предметных операциях берутся из Clock, а не из серверного NOW. Ограничения на будущую дату и уникальность имени группы не вводятся.

### Запись seed и очистка

Используем PostgreSQL INSERT с `ON CONFLICT (id) DO NOTHING`, чтобы пропускать только существующие идентификаторы. Другие нарушения целостности не скрываются. UUID и даты из JSON преобразуются к соответствующим типам. Сначала вставляются группы, затем занятия с учётом ссылки L7 на L6. Используется тот же загрузчик для команды, стартового entrypoint и reset; дополнительный запуск seed в lifespan не нужен.

Reset выполняет один DELETE всех занятий, затем DELETE групп, затем загрузку seed в той же транзакции. Удаление всех занятий одним SQL-запросом позволяет удалить вместе предшественников и преемников при NO ACTION. Альтернатива TRUNCATE не выбрана: обычный DELETE достаточен для малого набора и не требует каскадной очистки. Поведение проверяется на PostgreSQL.

### Проверки

Ограничения, миграции, идемпотентность seed и атомарность reset проверяются на отдельной тестовой PostgreSQL, не на рабочей БД. Схема создаётся миграциями, а не только `metadata.create_all`, чтобы тесты проверяли поставляемую схему. Подмены достаточны для отдельных HTTP-проверок, но не заменяют проверку ограничений PostgreSQL. Границы, ошибочные записи и разрешённые варианты покрываются сценариями спецификаций; повторяющиеся случаи параметризуются. Конкурентные преемники проверяются независимыми сессиями.

## Risks / Trade-offs

- Дополнительные слои увеличивают число файлов → сохраняем небольшие предметные модули без универсальных абстракций.
- Сохранение изменённых seed-записей может помешать восстановить другую отсутствующую запись из-за ограничения → загрузка откатывается, для полного восстановления используется reset.
- Autogenerate не гарантирует полный набор CHECK → ручное ревью миграции и проверки на PostgreSQL.
- Очистка тестовой БД разрушает её данные → отдельная явно выбранная БД; создание окружения и проверки с изменением данных выполняет пользователь после объяснения.

## Migration Plan

1. Добавить модели и их импорт в Alembic metadata.
2. Создать новую ревизию после 0001; проверить типы, именованные ограничения, upgrade и downgrade. Исходную ревизию не переписывать.
3. На отдельной БД проверить upgrade до head, загрузку seed, downgrade до 0001 и повторный upgrade. Downgrade удаляет предметные таблицы и их данные, поэтому выполняется только на тестовой БД.
4. Подключить загрузчик и API; проверить стартовый entrypoint с SEED_ON_START включённым и выключенным.

# Design

## Context

WP-03 реализует FR-01 и FR-02 поверх моделей, миграций и операций чтения WP-01 и сборки справочных данных WP-02. Формы запросов и ответов определяет `openapi.yaml`, порядок проверок — TASK.md §3.2.

## Decisions

### Общая проверка и HTTP-граница

Оба маршрута принимают одну схему `LessonCreate`. На HTTP-границе проверяются форма запроса, типы и формат данных. JSON с неверным типом поля получает `400 BAD_REQUEST`. Дата без смещения получает `422 VALIDATION_ERROR` с именем поля в `details.fields`. Предметные проверки выполняются в сервисе в следующем порядке.

1. BR-01 проверяет длительность по фактически прошедшему времени. Границы 30 минут и 8 часов включены. Для нарушения используем `details.fields.ends_at`.
2. BR-02 проверяет соответствие формата и аудитории. Для `IN_PERSON` без аудитории возвращаем `CLASSROOM_REQUIRED` с пустым `details`. Для `ONLINE` с аудиторией возвращаем `VALIDATION_ERROR` с `details.fields.classroom_id`.
3. BR-03 проверяет локальную группу, затем вызывает существующий сборщик. Отсутствие группы даёт `GROUP_NOT_FOUND` с `group_id` и завершает проверку до сети. Внутри сборщика действует приоритет `504 → 502 → INSTRUCTOR_NOT_FOUND → CLASSROOM_NOT_FOUND`. Запрос аудитории выполняется только для `IN_PERSON`.
4. BR-04 проверяет вместимость аудитории для `IN_PERSON`. При равенстве вместимости и размера группы проверка проходит.
5. BR-05 проверяет пересечения с активными занятиями.
6. BR-06 и BR-07 добавляют предупреждения о нагрузке и доступности.

Ожидаемые ошибки представлены в сервисном слое и преобразуются централизованно на HTTP-границе. Первый hard-отказ завершает проверку. `validate` преобразует отказ BR-04 или BR-05 в один элемент `violations` с теми же `code`, `message` и `details`, которые вернул бы `409`. В этом случае `ok: false` и `warnings: []`. При успешной проверке `validate` возвращает `ok: true`, пустой `violations` и рассчитанные предупреждения.

Общая проверка получает данные занятия и зависимости явно. Опциональный ID исходного занятия исключает его из BR-05 и BR-06 при будущих редактировании и переносе. Проверка текущего статуса и изменение исходной записи относятся к сценариям этих операций.

### Конфликты

Репозиторий выбирает активные занятия с совпадением по преподавателю, группе или ненулевой аудитории и условием `existing.starts_at < candidate.ends_at AND existing.ends_at > candidate.starts_at`. Активные статусы — `PLANNED`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`. Смежные интервалы допустимы.

Сервис даёт один элемент на каждую пару «занятие и совпавший ресурс». Пересечение вычисляется как максимум начал и минимум окончаний. Занятия идут по `starts_at`, затем `id`. Внутри занятия ресурсы идут в порядке `instructor`, `classroom`, `group`. Для границ пересечения и полей времени занятия сериализация через `to_iso_z` сохраняет дробные секунды, если они есть.

### Транзакция и одновременные запросы

Сервис создания открывает один `session_scope`. Группу читает до вызова people-stub, блокировки берёт после получения справочных данных и успешного BR-04. Каждому ресурсу соответствует стабильный числовой ключ из типа ресурса и UUID. Все операции берут транзакционные блокировки через `pg_advisory_xact_lock` в порядке числовых ключей, убирая дубликаты. Совпадение ключей для разных ресурсов может вызвать лишнее ожидание. Проверка BR-05 по-прежнему сравнивает сами UUID.

После захвата блокировок BR-05 выполняет отдельный запрос. При `READ COMMITTED` он видит уже зафиксированную запись запроса, который удерживал ключ. Если блокирующая транзакция откатилась, ожидающий запрос продолжает проверку по сохранённому расписанию. Сервис рассчитывает предупреждения и вставляет занятие в той же транзакции. Новый ID создаётся через UUID v4, `created_at` и `updated_at` получают одно значение `Clock`. Ответ `201` возвращается после успешного commit. При выходе из транзакции PostgreSQL освобождает блокировки.

Блокировка строк занятий через `SELECT FOR UPDATE` требует уже существующей строки. Транзакционные блокировки по ключу охватывают и первое занятие по ресурсу. На стороне БД продолжают действовать существующие ограничения интервала, формата и внешнего ключа группы. За BR-05 отвечает протокол записи сервиса. Прямой SQL и служебный seed могут его обойти. Для `validate` достаточно чтения. Его ответ отражает состояние на момент проверки и не резервирует ресурсы. Вызовы `create` и `validate` не порождают событий.

### Нагрузка преподавателя и доступность

Для BR-06 дни определяются в часовом поясе профиля преподавателя. Репозиторий ищет все активные занятия этого преподавателя, пересекающие затронутые новым занятием локальные сутки. Для каждого дня суммируем фактическую длительность пересечений с его границами, включая новое занятие. Занятие через полночь распределяется между днями. Окончание ровно в полночь не затрагивает следующий день. Сравнение с лимитом выполняется до округления. При строгом превышении добавляем по одному `WORKLOAD_SOFT_LIMIT` за дату в хронологическом порядке. `details` содержит локальную дату `YYYY-MM-DD` и числовые `max_hours`, `planned_hours`.

Для BR-07 используем часовой пояс ответа о доступности и ISO-дни недели. Занятие должно целиком помещаться в одно окно. Допустимы начало ровно на левой границе и окончание ровно на правой. Смежные окна рассматриваются по отдельности. Занятие через локальную полночь и пустой список окон дают `INSTRUCTOR_UNAVAILABLE` с `instructor_id`. Это предупреждение идёт после предупреждений о нагрузке.

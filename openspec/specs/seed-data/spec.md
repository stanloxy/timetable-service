# seed-data Specification

## Purpose
Обеспечить детерминированную загрузку исходных данных и восстановление тестового состояния без изменения часов сервиса (NFR-03).

## Requirements

### Requirement: Deterministic seed data
Система SHALL загружать группы и занятия из выданных файлов seed, сохраняя значения всех полей, включая UUID, ссылки, статусы и временные поля.

#### Scenario: Load an empty database
- **WHEN** seed загружается в пустую БД с применёнными миграциями
- **THEN** сохраняются ровно 3 группы и 8 занятий
- **AND** значения всех полей соответствуют файлам seed, включая ссылку L7 на L6

### Requirement: Idempotent non-destructive seed
Система SHALL при обычной загрузке добавлять отсутствующие seed-записи без дубликатов, сохраняя существующие записи и дополнительные предметные данные.

#### Scenario: Load seed repeatedly
- **WHEN** seed повторно загружается в БД с ранее загруженным seed
- **THEN** загрузка завершается успешно без создания дубликатов

#### Scenario: Restore missing seed records
- **WHEN** загружается seed, часть записей которого отсутствует в БД, а существующие данные не препятствуют их восстановлению
- **THEN** недостающие записи добавляются
- **AND** существующие записи сохраняются без изменений

#### Scenario: Preserve an edited seed record
- **WHEN** повторно загружается seed после допустимого изменения полей существующей seed-записи
- **THEN** загрузка завершается успешно
- **AND** изменённые значения существующей записи сохраняются

#### Scenario: Preserve additional lessons
- **WHEN** загружается seed в БД с дополнительным корректным занятием вне файлов seed
- **THEN** дополнительное занятие сохраняется без изменений

### Requirement: Explicit seed command
Система SHALL поддерживать загрузку seed командой `just seed` в БД приложения.

#### Scenario: Run the seed command
- **WHEN** выполняется `just seed` при доступном контейнере приложения и подготовленной БД
- **THEN** применяется обычная идемпотентная загрузка seed
- **AND** команда успешно завершается после фиксации данных

### Requirement: Optional seed on container startup
Система SHALL выполнять обычную загрузку seed при старте контейнера после миграций и до запуска приложения, если `SEED_ON_START=1`. При `SEED_ON_START=0` автоматическая загрузка SHALL отсутствовать.

#### Scenario: Start with automatic seed enabled
- **WHEN** контейнер приложения запускается с `SEED_ON_START=1` и миграции успешно применены
- **THEN** seed загружается до запуска приложения
- **AND** существующие данные обрабатываются по правилам обычной идемпотентной загрузки

#### Scenario: Start with automatic seed disabled
- **WHEN** контейнер приложения запускается с `SEED_ON_START=0`
- **THEN** автоматическая загрузка seed не выполняется

### Requirement: Reset test data
Система SHALL при `TEST_MODE=1` обрабатывать `POST /__test/reset` очисткой предметных данных и восстановлением исходного seed с ответом `204` без тела.

#### Scenario: Restore the initial dataset
- **WHEN** вызывается `POST /__test/reset` при `TEST_MODE=1` после изменения seed-записей и добавления дополнительных занятий
- **THEN** ответ имеет статус `204` и пустое тело
- **AND** в БД остаются ровно группы и занятия из файлов seed с исходными значениями всех полей

#### Scenario: Reset repeatedly
- **WHEN** `POST /__test/reset` вызывается повторно при `TEST_MODE=1`
- **THEN** каждый вызов завершается ответом `204`
- **AND** итоговые данные совпадают с исходным seed

### Requirement: Preserve service clock on reset
Система SHALL при сбросе данных сохранять состояние часов сервиса, включая зафиксированное время и режим часов.

#### Scenario: Preserve frozen time
- **WHEN** часы зафиксированы на `2026-11-30T03:00:00Z` и успешно вызывается `POST /__test/reset`
- **THEN** часы остаются зафиксированными на `2026-11-30T03:00:00Z`

#### Scenario: Preserve system clock mode
- **WHEN** часы работают в системном режиме и успешно вызывается `POST /__test/reset`
- **THEN** часы продолжают работать в системном режиме

### Requirement: Hide reset outside test mode
Система SHALL отвечать на `POST /__test/reset` при `TEST_MODE=0` статусом `404` с кодом `NOT_FOUND` в формате ошибок платформы, не изменяя данные.

#### Scenario: Reject reset outside test mode
- **WHEN** вызывается `POST /__test/reset` при `TEST_MODE=0`
- **THEN** ответ имеет статус `404` и код ошибки `NOT_FOUND`
- **AND** данные и состояние часов не изменяются

### Requirement: Atomic seed and reset
Система SHALL применять каждую загрузку seed и каждый reset атомарно: при ошибке записи все изменения соответствующей операции откатываются.

#### Scenario: Roll back failed seed loading
- **WHEN** при загрузке seed после успешной записи части данных возникает ошибка записи
- **THEN** все изменения этой загрузки откатываются
- **AND** ранее существовавшие данные остаются неизменными

#### Scenario: Roll back failed reset
- **WHEN** после очистки данных во время reset возникает ошибка восстановления seed
- **THEN** очистка и частичное восстановление откатываются
- **AND** данные возвращаются в состояние до вызова reset
- **AND** операция не возвращает успешный ответ `204`

### Requirement: Seed independence from domain validation
Система SHALL загружать seed напрямую, без вызовов people-stub и предметной валидации, сохраняя действие ограничений целостности БД.

#### Scenario: Load without people-stub
- **WHEN** seed загружается при недоступном people-stub
- **THEN** загрузка корректных seed-данных завершается успешно без запросов к people-stub и без предметной валидации

#### Scenario: Reset without people-stub
- **WHEN** вызывается reset при `TEST_MODE=1`, недоступном people-stub и доступной подготовленной БД
- **THEN** исходный seed восстанавливается с ответом `204` без запросов к people-stub и без предметной валидации

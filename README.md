## Запуск

<!-- Команды запуска, выбранный брокер (и почему), как проверить готовность. Ниже — то, что уже работает в каркасе. -->

```bash
just doctor      # проверка окружения: Docker, Compose v2.20+, buildx 0.17+, uv 0.13+
docker compose up --build   # так стек запускает проверка; .env не нужен
just up          # то же в фоне с ожиданием healthcheck: app, postgres, people-stub, брокер
just migrate     # alembic upgrade head в контейнере app (entrypoint делает это и при старте)
just seed        # загрузка seed (python -m app.maintenance.seed)
just check       # ruff + mypy + pytest tests/unit
just e2e-public  # публичные e2e против поднятого стека → e2e-report.json
just setup       # шаблон коммита и хук проверки (CONTRIBUTING.md)
curl -s localhost:8000/health/ready
```

Брокер: RabbitMQ (по умолчанию в docker-compose.yml) — ...

Служебные операции находятся в `app/maintenance`.
Загрузка выполняется через `just seed`, для отдельной тестовой БД —
через `just test-db-seed`. Внутренняя команда:
`python -m app.maintenance.seed`.

Для проверок миграций и данных используется отдельная временная PostgreSQL:

```bash
just test-db-init  # создать локальный .env.test со случайным паролем (не перезаписывает)
just test-db-up    # запустить только тестовую БД и дождаться готовности
just test-db-ps    # проверить состояние
just test-db-migrate # применить существующие миграции к тестовой БД
just test-db-seed # загрузить seed в тестовую БД
just test-app # приложение с тестовой БД: 127.0.0.1:8001
just test-container-build # собрать образ для проверки entrypoint
just test-container-start 0 # миграции без автоматического seed
just test-container-start 1 # миграции и автоматический seed
just test-db-migration "create groups and lessons" # создать ревизию, не применяя её
just test-db-down # удалить тестовый контейнер вместе с его данными
```

Тестовая БД доступна только на `127.0.0.1:55433`, имя базы — `wa_wp01_test`.
Пароль хранится в исключённом из Git файле `.env.test` с правами 600, без шифрования.
Не публикуйте содержимое этого файла или развёрнутый вывод `docker compose config`.
Данные временные: остановка контейнера теряет содержимое PostgreSQL; последующий запуск
требует повторного применения миграций. Основная БД и её том не затрагиваются.
Миграции и тесты с хоста должны явно получать подключение к тестовой БД;
эти команды не меняют основной `DATABASE_URL` и не применяют миграции автоматически.

Рецепты `test-db-migrate` и `test-db-migration` получают подключение через общий
`tools/test_db.py` из `.env.test` (или одноимённых `TEST_POSTGRES_*` переменных окружения).
Основной `DATABASE_URL` заменяется только в процессе Alembic, пароль не выводится.
Перед генерацией ревизии тестовая БД должна быть на текущем head: сначала
`just test-db-migrate`, затем `just test-db-migration "описание"`. Созданную миграцию
нужно отревьюить; применяйте её отдельным вызовом `just test-db-migrate`.

Интеграционные проверки выполняются с хоста против тестовой PostgreSQL:

    just test-db-up
    just test-db-migrate
    just test-db-test

Тесты БД разделены по темам в `tests/integration/db/`.
Обычные тесты откатывают свои изменения; конкурентный тест использует
независимые транзакции с commit и удаляет созданные им данные.

Seed/reset проверяются в `tests/integration/maintenance/`: точность данных,
идемпотентность, сохранение дополнительных записей, восстановление seed, часы,
HTTP-ответы и rollback при ошибке. Порядок команд entrypoint покрыт модульными
тестами. На текущем этапе пройдены 69 интеграционных и 22 модульных теста.
В настоящем контейнере проверены оба режима: после удаления L8 из тестовой БД
`just test-container-start 0` оставил 7 занятий, а `just test-container-start 1`
восстановил 8 занятий, включая L8 со статусом `COMPLETED`.
Файл `.env.test` исключён как из Git, так и из Docker-контекста.

После запуска `just test-app` с загруженным seed группу и занятие можно прочитать по UUID:

```bash
curl http://127.0.0.1:8001/groups/9a000000-0000-4000-8000-000000000001
curl http://127.0.0.1:8001/lessons/3d000000-0000-4000-8000-000000000001
```

## Решения

<!-- Принятые решения с альтернативами и причинами, включая решения по ситуациям, которые задание не регулирует. -->

- WP-01 — транзакции: используем существующий `session_scope` через `async with` вокруг всей операции. Для предметных сценариев выбрано открытие блока в сервисе, получающем фабрику сессий; маршрут передаёт фабрику из AppContext. Репозитории и загрузчик seed получают сессию без самостоятельного commit; очистка и восстановление при reset входят в одну транзакцию. Отдельный менеджер не вводим: каркас уже обеспечивает commit и rollback. Реализация предметных сервисов остаётся в задачах чтения WP-01.
- WP-01 — seed: обычная загрузка добавляет отсутствующие записи, сохраняя изменённые seed-записи и дополнительные данные. Перезапись при обычной загрузке отвергнута, чтобы повторный запуск не затирал изменения; исходное состояние восстанавливает reset. Seed выполняется отдельно от миграций и напрямую, без people-stub и предметной валидации.
- WP-01 — история переноса: кроме FK и уникальности предшественника запрещаем самоссылку и удаление используемых групп и исходных занятий. Это защищает ссылки и историю; каскадное удаление отвергнуто, поскольку могло бы удалить связанные занятия.

- WP-01 — структура: инфраструктура БД объединена в `app/db`, служебные операции — в `app/maintenance`. Размещение служебного reset в бизнес-слое отвергнуто; `services` предназначен для классов предметных сервисов.
- WP-01 — схемы: для Pydantic-схем запросов и ответов выбран отдельный `app/schemas`, маршруты остаются в `app/api`. Совместное размещение отвергнуто для отделения описания данных от HTTP-маршрутизации; перенос существующих служебных схем запланирован без изменения API.
- WP-01 — ошибки: согласована иерархия ServiceError с ResourceNotFoundError без HTTP-статусов; преобразование в контрактный ответ выполняется централизованно в errors.py с сохранением ApiError. Для технических ошибок БД остаётся иерархия SQLAlchemy: универсальная DatabaseError не добавляет поведения. Реализация и проверки включены в tasks.
- WP-01 — логирование: сохраняем стандартный logging и LOG_LEVEL. Запланирована запись неожиданной HTTP-ошибки с traceback в общем обработчике при безопасном ответе 500; повторные записи по слоям и traceback для ожидаемых отказов не нужны. Новые библиотеки и отдельная инфраструктура логов не вводятся.
- Правила работы с проектом закреплены в [AGENTS.md](AGENTS.md); нормативные требования и процесс остаются в TASK.md, контрактах, CONTRIBUTING.md и OpenSpec.
- WP-01 — запуск seed: все вызовы переведены на `python -m app.maintenance.seed`. Совместимая обёртка `app/seed.py` удалена: её внешних потребителей нет, а собственные вызовы обновлены.
- WP-01 — ограничения: в Python используются LessonStatus и LessonFormat на основе StrEnum из `app/enums/lessons.py`; SQLAlchemy преобразует их в строковые значения VARCHAR с существующими CHECK в PostgreSQL. Отдельные PostgreSQL enum-типы не создаются; произвольные строки в аннотациях ORM заменены enum ради типизации и автодополнения. PK объявляется через `primary_key=True`; дополнительное объявление PrimaryKeyConstraint ради имени убрано как избыточное.
- WP-01 — тестовая БД: отдельная PostgreSQL в Docker с временным хранилищем и локальным исключённым из Git файлом подключения. Использование основной БД для разрушающих проверок отвергнуто.
- WP-01 — тесты: pytest запускается с хоста против настоящей PostgreSQL. Обычные проверки изолированы транзакциями; конкурентная использует отдельные соединения, commit и собственную очистку. Подмена PostgreSQL не доказывает работу её ограничений.

## Запуск

Для запуска нужны Docker Compose v2.20+ и buildx 0.17+. Для локальных проверок нужны
uv 0.13+ и just. Установка описана в [SCAFFOLD.md](SCAFFOLD.md#окружение).
Из корня чистого клона запустите стек с настройками Compose по умолчанию.
Файл `.env` не требуется.

```bash
just doctor
docker compose up --build
```

Из второго терминала проверьте готовность.

```bash
curl -sS -i http://127.0.0.1:8000/health/ready
```

Ожидаются HTTP `200` и тело `{"status":"ok","db":"ok","broker":"ok"}`.
При отказе PostgreSQL или RabbitMQ readiness возвращает `503` со статусом каждой
зависимости. Встроенный healthcheck контейнера проверяет `/health/live`, который
показывает, что процесс приложения отвечает.

При старте контейнер приложения выполняет `alembic upgrade head`. Для ручного
применения миграций в поднятом стеке есть `just migrate`. Данные загружаются
по команде `just seed` или при запуске с `SEED_ON_START=1`.

Compose по умолчанию использует `BROKER=rabbitmq` и задаёт `BROKER_URL`.
События публикуются в topic exchange `wa.events` с ключами `timetable.<EventType>`.

### Проверки из чистого клона

Для gate нужен чистый клон проверяемого SHA, новый проект Compose с пустым томом
и свободные порты `5432`, `5672`, `8000`, `8100` и `15672`. Используйте
чистый сеанс Bash со значениями подключения и `TEST_MODE` по умолчанию.
Для клона опубликованной версии укажите SHA проверяемого коммита. До публикации
можно использовать локальный репозиторий как источник для `git clone --no-local`
и выбрать SHA коммита ветки пакета.

```bash
read -r -p 'SHA проверяемого коммита: ' candidate_sha
git clone https://github.com/stanloxy/timetable-service.git timetable-review &&
  cd timetable-review &&
  git switch --detach "$candidate_sha" &&
  sha="$(git rev-parse HEAD)" &&
  printf 'Проверяемый SHA: %s\n' "$sha" &&
  just doctor
```

В Bash запустите стек и замерьте время до первого HTTP `200` от readiness. Предел —
пять минут от запуска. Лог сборки и ответ readiness сохраняются вне клона.

```bash
export COMPOSE_PROJECT_NAME="timetable-review-$(date +%s)-$$"
review_logs="$(mktemp -d)"
SECONDS=0
docker compose up --build </dev/null >"$review_logs/compose.log" 2>&1 &
compose_pid=$!
status=000
while (( SECONDS < 300 )) && kill -0 "$compose_pid" 2>/dev/null; do
  status="$(curl -s --max-time 2 -o "$review_logs/ready.json" -w '%{http_code}' \
    http://127.0.0.1:8000/health/ready || true)"
  if [[ "$status" == 200 ]]; then
    break
  fi
  sleep 1
done
elapsed="$SECONDS"
printf 'Readiness: HTTP %s за %s с. Логи: %s\n' "$status" "$elapsed" "$review_logs"
test "$status" = 200 && test "$elapsed" -le 300 && cat "$review_logs/ready.json"
```

Перед переходом к тестам проверьте оба статуса зависимостей в теле ответа
и убедитесь по логам, что entrypoint применил миграции на пустой БД.
Публичные сценарии меняют данные, часы приложения, состояние заглушки и тестовую очередь
брокера. Запускайте их в том же изолированном проекте с `TEST_MODE=1`.

## Решения

<!-- Принятые решения с альтернативами и причинами, включая решения по ситуациям, которые задание не регулирует. -->

- WP-01 — транзакции. Предметный сервис открывает существующий `session_scope` вокруг всей операции с фабрикой сессий из контекста приложения. Репозитории получают сессию и выполняют операции хранения, а `session_scope` централизованно выполняет commit или rollback. При reset очистка и восстановление данных входят в одну транзакцию.
- WP-01 — seed: обычная загрузка добавляет отсутствующие записи, сохраняя изменённые seed-записи и дополнительные данные. Перезапись при обычной загрузке отвергнута, чтобы повторный запуск не затирал изменения; исходное состояние восстанавливает reset. Seed выполняется отдельно от миграций и напрямую, без people-stub и предметной валидации.
- WP-01 — история переноса: кроме FK и уникальности предшественника запрещаем самоссылку и удаление используемых групп и исходных занятий. Это защищает ссылки и историю; каскадное удаление отвергнуто, поскольку могло бы удалить связанные занятия.

- WP-01 — структура: инфраструктура БД объединена в `app/db`, служебные операции — в `app/maintenance`. Размещение служебного reset в бизнес-слое отвергнуто; `services` предназначен для классов предметных сервисов.
- WP-01 — схемы. Pydantic-схемы в `app/schemas` описывают данные независимо от маршрутизации в `app/api`.
- WP-01 — ошибки. Предметные ошибки наследуются от `ServiceError` и преобразуются в контрактные HTTP-ответы обработчиками. Технические ошибки БД используют иерархию SQLAlchemy. Общий HTTP-обработчик записывает неожиданные ошибки с traceback и возвращает клиенту общий ответ `500`. Уровень стандартного `logging` задаётся через `LOG_LEVEL`.
- Правила работы с проектом закреплены в [AGENTS.md](AGENTS.md); нормативные требования и процесс остаются в TASK.md, контрактах, CONTRIBUTING.md и OpenSpec.
- WP-01 — запуск seed: все вызовы переведены на `python -m app.maintenance.seed`. Совместимая обёртка `app/seed.py` удалена: её внешних потребителей нет, а собственные вызовы обновлены.
- WP-01 — ограничения: в Python используются LessonStatus и LessonFormat на основе StrEnum из `app/enums/lessons.py`; SQLAlchemy преобразует их в строковые значения VARCHAR с существующими CHECK в PostgreSQL. Отдельные PostgreSQL enum-типы не создаются; произвольные строки в аннотациях ORM заменены enum ради типизации и автодополнения. PK объявляется через `primary_key=True`; дополнительное объявление PrimaryKeyConstraint ради имени убрано как избыточное.
- WP-01 — тестовая БД: отдельная PostgreSQL в Docker с временным хранилищем и локальным исключённым из Git файлом подключения. Использование основной БД для разрушающих проверок отвергнуто.
- WP-01 — тесты. Интеграционные проверки используют PostgreSQL, чтобы проверить ограничения и транзакции самого движка. Обычные проверки откатываются, а конкурентные сценарии используют отдельные соединения, commit и собственную очистку.
- WP-02 — HTTP-клиент: используем `httpx` как зависимость приложения и переиспользуем клиент в течение `lifespan`. На каждый вызов действует общий `STUB_TIMEOUT_MS` через `asyncio.timeout()`. Таймауты HTTPX по отдельным этапам не дают общего лимита.
- WP-02 — отказы people-stub: ждём все параллельные вызовы в пределах их таймаутов и выбираем ошибку в порядке `504`, `502`, `INSTRUCTOR_NOT_FOUND`, `CLASSROOM_NOT_FOUND`. Завершение при первом отказе было бы быстрее, но код ошибки зависел бы от порядка ответов. Сетевой сбой, некорректное тело ответа или неожиданный HTTP-статус отображаются как `502`.
- WP-02 — оценка 2 ч включает согласование OpenSpec, клиент и сборку данных, проверку ошибок и замера, документацию и завершение ветки.
- WP-03 — создание блокирует ресурсы по ключам из типа и UUID до конца транзакции. Отдельный поиск после захвата при `READ COMMITTED` видит уже зафиксированные занятия и позволяет вернуть все конфликты. Для `EXCLUDE` потребовались бы миграция и дополнительное чтение после конкурентного отказа. Создание, PATCH и перенос используют общий порядок захвата ключей.
- WP-03 — оба POST-маршрута выполняют проверки в одном порядке и останавливаются на первом hard-отказе. `validate` возвращает нарушения вместимости и расписания в `violations` и читает текущее состояние без резервирования ресурсов. Границы пересечений и время занятия передаются с дробными секундами при их наличии.
- WP-03 — нагрузку через полночь делим по местным дням преподавателя и предупреждаем за каждую дату со строгим превышением. Для доступности требуется одно окно целиком. Смежные окна проверяются по отдельности. Предупреждения возвращаются вместе с успешным ответом.
- WP-04 — список строит страницу и считает `total` одним SQL-запросом. Два запроса при `READ COMMITTED` могли бы увидеть разные состояния расписания. Равные и обратные границы периода дают пустой список. Ошибки параметров списка дают `422 VALIDATION_ERROR` по контракту GET.
- WP-04 — PATCH блокирует строку занятия, затем берёт те же ключи, что POST, по прежним и новым ресурсам в общем порядке. Так параллельные частичные правки применяются к актуальной строке, а создание ждёт завершения изменений на общих ресурсах. Для одного поля остаётся последняя успешно сохранённая правка. Исходное занятие исключается из расчёта пересечений и нагрузки.

- WP-05 — HTTP-переходы проверяют актуальный статус под блокировкой строки. Перенос берёт прежние и новые ключи ресурсов в общем порядке с POST и PATCH. Одна транзакция фиксирует исходное занятие и преемника, а уникальность `rescheduled_from_id` ограничивает число преемников.
- WP-05 — sweeper отбирает `CONFIRMED` по времени начала из `Clock`, блокирует подходящие строки в порядке ID и считает фактические обновления через `RETURNING`. Ручной и периодический запуск используют одну задачу.
- WP-06 — RabbitMQ даёт маршрутизацию по типам событий через topic exchange и подтверждение приёма через publisher confirms. Сервис формирует `LessonConfirmed`, `LessonCancelled` и `LessonRescheduled` в транзакции и ожидает результат публикации после успешного commit. При временном сбое адаптер может сделать до трёх попыток подготовки соединения, канала и exchange. На подготовку и публикацию вместе отведено две секунды.
- WP-06 — после вызова `publish` повторной отправки нет. Если подтверждение потерялось, повтор мог бы создать вторую копию уже принятого сообщения. При сбое адаптер пишет итог в журнал, а клиент получает штатный ответ о сохранённом переходе. При повторной доставке подписчик может использовать `idempotency_key`.
- WP-06 — readiness делает отдельные запросы к PostgreSQL и RabbitMQ параллельно. AMQP-соединение открывается по требованию и может восстановиться после отказа без перезапуска процесса.

## Не сделано

<!-- Что не сделано и почему. -->

- В текущей версии отсутствуют дополнительные сценарии TASK.md §4. Это серия занятий (`POST /lesson-series`, FR-14), отчёт недельной нагрузки преподавателя (FR-15), список групп с пагинацией (`GET /groups`, FR-16) и TTL-кэш people-stub (FR-17).
- Для обязательной части выбрана прямая публикация. Transactional outbox и восстановление потерянных событий не реализованы. При сбое между commit и доставкой событие может быть потеряно, а при потере подтверждения его исход может остаться неизвестным.
- Compose настроен для локальной проверки задания. Он использует публичные учётные данные `wa/wa` и включает служебные тестовые маршруты по умолчанию.


На фейковом клиенте каждый вызов ждёт 300 мс. В замере WP-02 последовательный
вариант занял **901,7 мс**, конкурентный — **301,4 мс**. Повторный замер
WP-07 на `b595adb` дал **904,0 мс** и **301,4 мс** соответственно.
Для очного занятия это примерно трёхкратный выигрыш.

и трёх активных вызовов и требует меньше 75% последовательного времени
для конкурентного запуска.
